# Delta Electronics Thailand

**Application Engineer**, IT manufacturing systems team · April 2026 to present

## What the role covers

DevOps, full-stack web development, and production line support for the factory's MES (Manufacturing Execution System) tooling, inside a fully air-gapped corporate network. Also acts as project manager on almost every initiative below: planning the work, coordinating with other departments to keep it moving, presenting it to the department, and supporting the people who use it afterward.

## What I built

**Production line support.** Troubleshoot MES, application, and data issues reported from the floor, and work with the people on the line until each one is resolved.

**CI/CD platform.** Built and maintain the GitLab CI/CD pipelines for `mfg-portal-frontend` (React/Vite) and `mfg-portal-api` (ASP.NET Core), deploying through a Rancher-managed Kubernetes cluster with images pushed to Harbor. Was the first person on the Thai team to put this Rancher/Kubernetes/GitLab CI-CD architecture together and present it to the whole IT department. Other application teams and the server team are now adopting it, and I'm the point of contact for that rollout.

**MES monitoring dashboard.** Full-stack dashboard (React, .NET 8, Docker Swarm) showing real-time service health and usage metrics.

**Yield Tracker Report.** Sole developer on a full-stack production yield reporting and drill-down tool for the QA team (React/TypeScript/Tailwind, ASP.NET Core/.NET 8, Oracle via ODP.NET, SQL Server holding query templates as config-as-data). Aggregates station-level pass/fail data across factories and models, with drill-down from summary down to individual repair records and Excel export via ExcelJS. Fixed an N+1 query in MO-to-model resolution, parallelized per-schema data fetching, added row virtualization for 10,000+ row tables without pagination, and traced a session-hydration race condition in the app's shared auth layer that had been silently breaking deep links app-wide. Deployed in Thailand with rollout planned for Taiwan and other sites; took about five days to build.

**CTP diagnostic tool.** ASP.NET Core API + React/TypeScript frontend that traces production data errors and incorrect data configurations on the lines. It automates cross-schema comparisons in Oracle (`PROD_SCHEMA_A` / `PROD_SCHEMA_B`), flagging MATCH/MISMATCH cases that used to be checked manually, and cross-references live factory data from MS SQL Server and PostgreSQL. Tuned the SQL queries and stored procedures to cut report time and fix data latency.

**MinIO object storage.** Set up and configured a MinIO deployment from scratch and advise other teams on how to deploy against it. Also run MinIO as a Docker container next to the requirement tracking backend below, for its attachments.

**Requirement request tracking.** Built the backend for the Requirement page, where people submit requests that move through MES, AP, IT Server and OA review stages until the user verifies the result. It is a Python FastAPI service on top of an existing SQL Server table that it may only read from and insert into: every change is a new snapshot row, the current state is the newest row per request (picked with `ROW_NUMBER()`), each write takes an `sp_getapplock` lock and checks the expected revision so a stale edit gets a 409, and an idempotency key returns the first result instead of writing twice. The workflow rules (which transitions are allowed, who may run each command, stage timestamps, and the task and work-item checks before User Verification) live in a pure module with its own tests. Attachments go to MinIO. The preview type comes from the file's real bytes, never its name, uploads are tied to a request with HMAC-signed tokens that cannot be reused or borrowed, and downloads go out with safe headers and a sandboxed content policy. Identity comes from a JWT, IT rights from the role table, and the database connection string is decrypted from a mounted file inside the container. It runs in Docker Compose next to its MinIO.

**AIFinance.** Led and built a system that finds the same company across Finance's monthly SAP exports (the customer master with sales and the vendor master with purchases), puts each company under its parent group, leaves out the company's own group companies, and adds up sales and purchases per group and per company in each currency. No file name or column is fixed in the code: the AI sees the headings with three sample values, every digit masked, to work out which column is which, and the rest runs in seven steps (read, normalize, exclude, match, group, check, summarize). Every number comes from pandas, never from the AI. The AI only answers narrow questions in batches, such as whether two names are one legal entity or which group a company belongs to, and it only ever sees company names and countries. Its answers are treated as claims: a YAML knowledge file of groups outranks them, a group answer is asked again as a yes or no question when the group's name is not in the company's name, and a person can overrule anything. Every answer is stored, so a second run asks nothing and takes seconds, and every record says how it was matched, who decided, and why. AI-written summaries drop any sentence holding a number they were not given. A web backend with finance, IT and admin roles takes a month from upload through review to release, exports to Excel with native charts, PDF, Word and PowerPoint in English, Thai and both Chinese scripts, and lets IT edit the knowledge file one entry at a time with checks, proposals and undo. Runs go through a NATS JetStream queue to Python workers, and the network-heavy parts are moving into Go services: an edge that balances the API copies, an AI gateway client that paces every worker against the shared per-minute quota, and an ops service that scales workers by queue depth. Coordinated with Finance and designed the architecture as project manager.

**Central NiFi platform.** Set up and run a dedicated NiFi cluster, separate from the team's shared production clusters, as a central platform that IT and other teams build their own flows on. Used as middleware for logging, alerting, data migration, and routing data across multiple systems, including running scripts for MinIO job work. Presented this to the department as well.

**AI OpenSearch log analytics platform.** Built the log analysis platform for the factory's MES. It pulls the logs of the API gateway, the routing service, the SMT machine service and the IoT data aggregators into OpenSearch, shows them in two web frontends (a page inside the MES portal and the AI OpenSearch page in AI Center), explains them with an AI assistant, and alerts Teams when production is hurt. The always-running ingest path is in Go with only the standard library: a collector lists every source's log folders each minute and downloads only the new bytes of each file with HTTP Range requests, workers run the parsers and scale between a lowest and highest count by queue length, an importer writes daily OpenSearch indices, and an ops service reports every container's state, health, CPU and memory. The live file can be read every minute, so logs and alerts run one to two minutes behind instead of waiting for the file to rotate, and each record's id is a hash of its line, so a line imported twice overwrites itself. The API, the parsers and the assistant stay in Python and FastAPI. The parsers split gateway errors into exception, root cause, class and method, keep SQL apart so only IT sees it, pull out failed test rows and out-of-limit measurements, and flag template values sent in place of real machine numbers. Nineteen alert rules sit in three levels (service down, API error, normal problem) and are judged on the logs' own clock, not the wall clock: each window ends at the newest record, a problem has to last its hold time, and only incidents still going in the newest minute are announced, while minutes judged during a catch-up are recorded without a message. Alerts go to seven Teams destinations as Adaptive Cards over a webhook, or as HTML to a channel email through the company mail server after the network blocked the webhook domain, all through an outbox with retries. The Issues page counts every problem once with where, when and the likely cause, and every Find in Search link and AI answer carries its exact scope (time, source and filters), so a click opens exactly the records it talks about. An external API with read, tune and admin keys lets other AI tools and scripts query and tune it, and every change it makes is logged and can be undone. CI/CD runs on a GitLab runner using the host's Docker, builds only the images whose content hash changed, and deploys the API blue/green behind nginx so the page never goes down. About 300 Python tests, Go unit tests and 140 Vitest tests run in CI.

**Central Kafka platform.** Built a shared Kafka platform that IT and other application teams can plug their own apps into, instead of each team standing up its own broker. A 3-broker cluster in KRaft mode (no ZooKeeper, replication factor 3, every node running broker, controller and JMX exporter), plus a separate tooling VM with AKHQ for topic and consumer lag inspection, Prometheus scraping each broker's JMX exporter, Grafana dashboards, and Redis for consumer services, all behind an nginx reverse proxy. Also specified the broker sizing (4 vCPU, 8 GB RAM, 50 GB OS + 300 GB data disk, RHEL 8.10, non-root) and the full port plan for the servers.

**Data pipeline design.** Separately from the Kafka and NiFi platforms themselves, designed the flows that pull data out and send it on: NiFi reads from the Oracle MES databases over CDC/JDBC and produces raw events into Kafka, Spark Structured Streaming on the existing data processing cluster consumes the raw topics and writes cleaned gold topics, and Airflow workflows schedule the Spark jobs every 15 to 30 minutes.

**Data investigation.** Traced a `shipment_code` vs internal `unit_serial` mismatch across the `PROD_SCHEMA_B` schema to support a live MES rework case.

**AI Center, AI Deltron and AI Monitor.** Built AI Center, the web portal that brings together every AI project the team has built in the company, and the services behind it. The React portal holds the app launcher for those projects, people and credits pages with staff photos, the AI Deltron chat, the AI OpenSearch log page, and AI Monitor, an admin console for every AI project with views for usage, chat logs, knowledge, prompts, evaluation, AI gateway use, services and the audit log. AI Deltron is the assistant that answers from the company's own knowledge: retrieval over documents synced from SharePoint and Confluence and past ServiceDesk Plus (SDP) ticket resolutions, embedded with Qwen models and answered through the company AI gateway, with reranking, vision-language models for scanned documents, and speech-to-text for audio. Knowledge is built in stages: prepared documents reviewed before publishing, structured data tables the model can call as tools, a document graph of attachments and versions, a change log that shows what an update touches, evaluation runs scored per chat mode, and chat modes kept as data with an Auto mode that picks one. Conversations are logged to build fine-tuning datasets. The backend started as one FastAPI app and was split one step at a time, each step undoable by pointing the edge back: one Python image that runs as the api, worker, media or chat role, plus Go services for the edge router, container scaling, an AI gateway proxy that shares the per-minute quota between projects and queues instead of failing on 429, and the AI Monitor numbers. Postgres with pgvector, MinIO, NATS JetStream and Gotenberg sit underneath. Staff photos come from the HR service through an NTLM login, are cached weekly as WebP, and fall back to the viewer's own login and then to initials. Every page works at phone, tablet and desktop width, and the screen logic lives in classes with unit tests.

**Observability stack.** Set up Prometheus and Grafana for metrics, and OpenSearch for centralized log storage and search across the team's services.
